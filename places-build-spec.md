# Places — Build Spec (v2)

A Place is a small, bounded 3D scene (cabin clearing, airport hotel room, whatever reference you pick), fixed and hand-authored, not procedurally generated at runtime. Every object is created once via code/generation tools, then placed at a fixed position. The only things that change while someone's inside are object movement (a plane along its path) and weather. Walkable with real collision, flyable in a free-cam mode. Hand this to Claude Code as the project brief.

## Core principles

- **Enclosed and fixed, not procedural, not infinite.** Nothing about a Place's layout is generated at runtime or varies between sessions. The terrain, the walls, every object's position, is fixed data, authored once. The only things that change while someone's inside are object *movement* (the plane along its path) and *weather* (rain/snow intensity, lighting mood). Everything else is exactly the same every time.
- **Code-generated assets, not reconstructed, not runtime-procedural.** No 3DGS, no photogrammetry, no uploaded photos as source geometry, and no Perlin-noise-style generation deciding what the scene looks like. Every object is either hand-built Three.js geometry or generated once via img2threejs from a reference image, then placed at a fixed, authored position. Real geometry means real collision, real dynamic lighting, and real weather.
- **Two camera modes with different physics:**
  - **Walk mode**: gravity, ground collision, wall/object collision, calm capped speed (this is the "slow walking in a relaxing landscape" mode, deliberately unhurried).
  - **Free-cam mode**: no collision, flies through geometry, for looking around or getting an establishing view.

## Architecture

### 1. Data model layer (borrowed from the ASCII City project's approach)

Keep a plain data description of the scene separate from the Three.js rendering, the renderer just reads this and draws it. This is what makes collision, boundaries, and later edits cheap instead of tangled into render code.

```js
// scene-data.js
export const sceneBounds = { minX: -8, maxX: 8, minZ: -8, maxZ: 8 };

export const colliders = [
  { type: 'box', center: [0, 1, -6], size: [4, 2, 0.3] },   // cabin back wall
  { type: 'box', center: [-6, 1, 0], size: [0.3, 2, 12] },  // left tree line / fence
  // ...
];

export const objects = [
  { id: 'cabin', factory: 'createCabinModel', position: [0, 0, -6], rotation: 0 },
  { id: 'plane', factory: 'createPlaneModel', position: [30, 8, -40], path: 'takeoffPath' },
  // ...
];
```

`factory` names map to the `THREE.Group` factories generated by img2threejs (see below). This also means swapping an object's look later is a one-line change, not a re-export.

### 2. Terrain / shell (adapting SlowRoads' rendering tricks, not its generation)

SlowRoads' generation itself (heightmaps, road-routing, anything decided at runtime) doesn't apply here, a Place's terrain is authored once and stays fixed. But two of its *rendering* tricks are worth reusing directly, since they're about rendering cost, not about generating layout:

- **Near/far detail grids**: rather than one uniform-resolution ground mesh, author a higher-detail mesh near the walkable area and a coarser one at the visual edges (distant treeline, sky-level terrain). Cheaper to render, and detail effort goes only where the player will actually get close. Both are fixed, hand-placed meshes, nothing is generated at runtime.
- **Instanced sprite foliage**: trees and bushes as instanced geometry with a few sprite variations, each instance's position and variant chosen once when the Place is authored and saved as fixed data, not re-rolled at runtime.

The ground material can still blend a couple of textures (snow, packed path, rock) in one shader for a cheap, smooth look, that's a rendering technique, not layout generation, the blend is driven by the fixed, authored geometry underneath it, not by anything randomized per session.

For lighting, SlowRoads deliberately kept it simple (top-down light, faked tree-shadow texture) to sidestep dynamic shadow cost. You have more headroom for a small bounded scene, real dynamic light + shadow maps are fine at this scale, and you'll want them anyway for the day/night or storm mood shifts.

### 3. Objects via img2threejs

For discrete objects (cabin exterior, furniture, luggage, a small plane model, window frame details): clone the skill and run it per reference image.

```bash
git clone https://github.com/nano-step/img2threejs ~/.claude/skills/img2threejs
```

In Claude Code, per object:
```
/img2threejs Rebuild this object as a Three.js model, keep the proportions, angles, and colours.
```
(attach or point to the reference image for that one object)

This produces a TypeScript `THREE.Group` factory with pivots/sockets/colliders already set up, drop the output into your `objects/` folder and register it in `scene-data.js`.

## Camera modes and collision

### Walk mode

Ground collision via downward raycast each frame (keeps the camera pinned to terrain height), wall/object collision via simple capsule-vs-box checks against the `colliders` array from the data model.

```js
import * as THREE from 'three';

const WALK_SPEED = 1.2;      // deliberately slow, calm pace
const PLAYER_RADIUS = 0.35;
const EYE_HEIGHT = 1.6;
const raycaster = new THREE.Raycaster();

function resolveGround(position, groundMeshes) {
  raycaster.set(new THREE.Vector3(position.x, position.y + 5, position.z), new THREE.Vector3(0, -1, 0));
  const hit = raycaster.intersectObjects(groundMeshes, true)[0];
  return hit ? hit.point.y + EYE_HEIGHT : position.y;
}

function collidesAt(x, z, colliders) {
  for (const c of colliders) {
    if (c.type !== 'box') continue;
    const [cx, , cz] = c.center;
    const [sx, , sz] = c.size;
    if (Math.abs(x - cx) < sx / 2 + PLAYER_RADIUS && Math.abs(z - cz) < sz / 2 + PLAYER_RADIUS) {
      return true;
    }
  }
  return false;
}

function tryMove(camera, dx, dz, colliders) {
  const nx = camera.position.x + dx;
  const nz = camera.position.z + dz;
  if (!collidesAt(nx, camera.position.z, colliders)) camera.position.x = nx;
  if (!collidesAt(camera.position.x, nz, colliders)) camera.position.z = nz;
}
```

The scene's own bounding box (`sceneBounds`) doubles as the outer wall, so "enclosed" is enforced the same way as any other collider, not a special-cased hack this time, because it's real geometry now.

### Free-cam mode

Same `PointerLockControls`-style look, but `tryMove`/`resolveGround` are simply not called, movement applies directly to camera position with no checks. A single toggle key (e.g. `V`) swaps which update function runs per frame.

## Scripted path movement (the plane, or any future vehicle)

Note on provenance: the ASCII City project (Grow Now! Games) isn't open source, it's a closed prototype, so there's no published breakdown of its actual car-movement algorithm. Public write-ups only confirm the shape of the system (a grid-based world data model, generated in Rust, handed to a JS/WebGL raycasting renderer, with cars existing as entries in that grid), not the path-following logic itself. What follows is the standard technique this class of problem uses in general, not a reconstruction of ASCII City's specific implementation, and it's directly reusable for your plane.

Keep the path as plain data, consistent with the data-model layer described above:

```js
const takeoffPath = [
  [40, 0, -50],   // taxi start
  [10, 0, -50],   // runway threshold
  [-20, 2, -48],  // rotation / lift-off, y starts rising
  [-60, 15, -40], // climbing away
];

function pointOnPath(path, t) {           // t: 0-1 progress along the whole path
  const segments = path.length - 1;
  const scaled = t * segments;
  const i = Math.min(Math.floor(scaled), segments - 1);
  const localT = scaled - i;
  const a = new THREE.Vector3(...path[i]);
  const b = new THREE.Vector3(...path[i + 1]);
  return a.lerp(b, localT);
}

let progress = 0;
function updatePlane(dt) {
  progress = (progress + dt * 0.02) % 1;   // loop the takeoff every ~50s
  const pos = pointOnPath(takeoffPath, progress);
  planeObject.position.copy(pos);
  const ahead = pointOnPath(takeoffPath, Math.min(progress + 0.01, 1));
  planeObject.lookAt(ahead);               // orient nose toward travel direction
}
```

Call `updatePlane(dt)` in the main render loop, alongside `tryMove`/`resolveGround`.

If more than one scripted vehicle is ever wanted, the straight-lerp version above tends to look faceted at corners. Swap to a `THREE.CatmullRomCurve3` built from the same point list for smooth cornering, give each vehicle its own `progress` and speed, and add a simple spacing check against the vehicle ahead on the same curve so they don't overlap. For a single scripted plane crossing an enclosed clearing occasionally, none of that extra machinery is needed, the lerp version above is already the right amount of system.

## Weather system

- **Visual**: a rain/snow particle system (instanced `THREE.Points` or a shader-based particle system), toggled or intensity-scaled by a single `weatherIntensity` value.
- **Material response**: swap ground/roof materials to a higher-reflectivity variant when `weatherIntensity > 0`, cheap and reads well without needing real wetness simulation.
- **Audio response**: see below, rain intensity drives a live-synthesized sound, not a fixed file, so it can scale smoothly with the visual.

## Audio stack

Three layers, each suited to a different kind of sound:

### 1. Ambient base bed (airport hum, distant murmurs, room tone)

Generate once with an AI soundscape tool (e.g. Noiz, Plassemble's Ambiance Loops), prompt it directly for the mood: *"quiet airport hotel room at midnight, distant murmurs, occasional far-off plane, loop-safe."* Export a seamless WAV and loop it as a basic `THREE.Audio` (non-positional, it's the whole-room bed).

```js
import * as THREE from 'three';
const listener = new THREE.AudioListener();
camera.add(listener);

const ambientBed = new THREE.Audio(listener);
new THREE.AudioLoader().load('/audio/ambient-bed.wav', buffer => {
  ambientBed.setBuffer(buffer);
  ambientBed.setLoop(true);
  ambientBed.setVolume(0.4);
  ambientBed.play();
});
```

### 2. Positional one-offs (the plane taking off, distant chatter from one side of the room)

`THREE.PositionalAudio` attached directly to the moving object, or to a fixed anchor, so it pans and attenuates with position automatically.

```js
const planeSound = new THREE.PositionalAudio(listener);
new THREE.AudioLoader().load('/audio/plane-engine.wav', buffer => {
  planeSound.setBuffer(buffer);
  planeSound.setRefDistance(20);
  planeSound.setLoop(true);
  planeObject.add(planeSound);   // moves with the plane automatically
  planeSound.play();
});
```

### 3. Live-synthesized weather (rain, wind)

Use Tone.js for anything that should scale continuously and never sound like a looping file, rain built from filtered noise rather than a recording.

```js
import * as Tone from 'tone';

const rainNoise = new Tone.Noise('pink').start();
const rainFilter = new Tone.Filter(1200, 'lowpass').toDestination();
rainNoise.connect(rainFilter);
rainNoise.volume.value = -Infinity; // silent until weatherIntensity > 0

function setRainIntensity(amount) {           // amount: 0-1
  rainNoise.volume.value = amount > 0 ? -20 + amount * 20 : -Infinity;
}
```

## Agent/skill architecture for Claude Code

Three narrow specialist subagents, one shared style state that survives between them, and the main session as orchestrator. This matters because Claude Code subagents each start with a fresh context window and have no memory between invocations, consistency can't live in an agent's memory, it has to live in files on disk that every relevant agent reads (and some write) each time.

### Shared state files (the actual source of consistency)

- `docs/style-guide.json` — palette, material rules, a handful of mood adjectives (e.g. `"cold, quiet, sparse, warm accents"`). Created once from *all* reference photos together, before individual object generation starts, not derived one object at a time.
- `docs/sound-palette.json` — derived from the same mood adjectives: frequency range, reverb character, the ambient-bed prompt text. This is what keeps the audio mood matched to the visual mood instead of being invented independently.

### `.claude/agents/object-modeler.md`

```markdown
---
name: object-modeler
description: Generates a single 3D object (prop, furniture, cabin, plane, etc.) from one reference photo via the img2threejs skill, conforming to the shared style guide.
tools: Read, Write, Edit, Bash
---

You are the object-modeling specialist for this project.

1. Read docs/style-guide.json first. If it doesn't exist yet, stop and say so, it must
   be created by the style-colorist agent before any object generation.
2. Invoke the img2threejs skill on the reference image you were given.
3. Compare the generated object's material colors against the palette in
   style-guide.json. If any material deviates beyond a small tolerance, do not fix it
   yourself, flag it clearly in your final report so the style-colorist agent can
   review it.
4. Report the output file path and a short list of any flagged deviations.
```

### `.claude/agents/style-colorist.md`

```markdown
---
name: style-colorist
description: Establishes or audits the shared color/material palette (docs/style-guide.json) for the whole scene, and reviews generated objects for style drift.
tools: Read, Write, Edit
---

You are the style/color specialist for this project. You have two distinct modes,
the calling prompt will tell you which:

**Setup mode** (run once, before any objects exist): read all reference photos
provided, derive a shared palette and 3-5 mood adjectives, write docs/style-guide.json.

**Audit mode** (run after an object-modeler call flagged deviations): read the
flagged object's material values and docs/style-guide.json, apply the smallest
edit that brings it back in line with the palette, and note the change in
style-guide.json's object registry so drift is tracked over time.
```

### `.claude/agents/soundscape-composer.md`

```markdown
---
name: soundscape-composer
description: Handles Tone.js live synthesis, positional audio wiring, and ambient-bed prompt generation, kept coherent with the shared mood in docs/sound-palette.json.
tools: Read, Write, Edit, Bash
---

You are the audio specialist for this project.

1. Read docs/sound-palette.json first. If it doesn't exist yet, derive it from
   docs/style-guide.json's mood adjectives (the style-colorist agent's output),
   then write it.
2. For live/reactive sounds (rain, wind): write Tone.js noise+filter patches.
3. For scripted movers (the plane) or fixed positional sources (distant chatter):
   wire THREE.PositionalAudio attached to the relevant object.
4. For the one-time ambient bed: write the exact prompt text to hand to an AI
   soundscape tool, built from the same mood adjectives, don't invent a new mood.
```

### When to actually promote these to real subagents

Build the first 2-3 objects directly in your main Claude Code session using the img2threejs skill and a plain `style-guide.json` you maintain by hand. Promote to the three formal `.claude/agents/` files above once you're generating enough objects that style drift becomes a real, felt problem, not before. The orchestration (placing objects in `scene-data.js`, wiring colliders, positioning the plane's path, tying it all together) stays in the main session throughout, it needs the whole picture at once, which is the opposite of what narrow specialist agents are for.

## Suggested milestones

1. Data model + bare terrain shell (near/far grid, ground shader) with free-cam only, confirm the space reads right before adding anything else.
2. Walk mode: ground raycast + box colliders + slow walk speed, test the enclosed boundary feels natural, not like hitting an invisible wall.
3. Bring in img2threejs-generated objects (cabin/furniture/plane), wire their generated colliders into the data model. Start this directly in the main session (see Agent/skill architecture above), promote to the three specialist subagents once style drift becomes a real problem.
4. Ambient audio bed + positional plane/chatter sounds.
5. Weather: particles + material swap + Tone.js rain synthesis, tie all three to one `weatherIntensity` value.
6. Pass: tune fog/lighting at the boundary edges so "enclosed" reads as a natural clearing/room edge rather than a wall you bump into.

## Libraries/dependencies

- `three` — core rendering
- `@nano-step/img2threejs` (Claude Code skill, not an npm package) — per-object generation from reference images
- `tone` — live weather/ambience synthesis
- Three.js built-ins: `THREE.Audio`, `THREE.PositionalAudio`, `THREE.Raycaster`, `PointerLockControls`
- An AI soundscape tool of your choice (Noiz, Plassemble, etc.) for the one-time ambient bed export, used as a generation tool, not a source of real recordings
